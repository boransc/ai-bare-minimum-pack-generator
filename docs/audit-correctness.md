# Correctness audit — AI Bare Minimum Pack Generator

Scope: correctness only (no style, naming, or comment nits). Findings are ordered by severity. Each is marked PROVED (traced through the actual code path) or SUSPECTED (plausible, not exercised).

## Findings

### High — document field autosave can revert a newer edit to a stale one (race between debounced autosave and blur commit)

**File:** `components/document-fields-context.tsx`, `commit()` (lines 90–132), triggered from `setValue()` (lines 74–88) and `EditableBracket`'s `onBlur`/`onKeyDown` in `components/bracketed-text.tsx` (lines 103–112).

**Status: PROVED.**

`commit(fieldId, rawValue)` can be invoked twice for the same field while an earlier call's `fetch` is still in flight — e.g. the 900ms debounce timer fires a commit for an intermediate value, and before that request resolves the user finishes typing and blurs the field, firing a second, overlapping commit for the final value. Nothing in `commit` sequences these two calls: each one independently does

```
savedRef.current[fieldId] = trimmed        // optimistic, synchronous
fetch(...).then(body => {
  savedRef.current[fieldId] = body.fields[fieldId];
  setValues(current => applyFieldValue(current, fieldId, serverValue));
})
```

There is no per-field request counter or "is this response still the latest one" check. If the two responses arrive out of order (ordinary network jitter, no special conditions needed), the `.then` for the *older* request runs last and overwrites both `savedRef` and the on-screen `values` with the older value — silently discarding the value the user actually finished on. The next keystroke-triggered commit will treat the reverted value as the new baseline unless the user notices and retypes.

Concrete scenario:
1. User types "Jo" into the AI-lead-name bracket, pauses → debounce fires `commit("Jo")` → request A sent.
2. Before A resolves, user types "John" → `setValue` reschedules a new debounce timer.
3. User tabs to the next field before that new timer fires → `onBlur` fires `commit("John")` directly → request B sent while A is still outstanding.
4. Response B arrives first, sets the field to "John" (correct so far). Response A then arrives (e.g. was queued behind B at the edge or just slower) and its `.then` unconditionally applies "Jo" to both `values` and `savedRef`.
5. The input now visibly shows "Jo" again, and `savedRef` believes "Jo" is what the server holds — a later unrelated edit's "is this unchanged?" check (`trimmed === previouslySaved`) is now comparing against the wrong baseline too.

**Fix:** give each field a monotonically increasing request sequence number (e.g. `seqRef.current[fieldId]++` at the start of `commit`, captured in the closure) and ignore a response in `.then`/`.catch` if a newer sequence number has since been issued for that field. Alternatively, make `commit` itself cancel/supersede any in-flight request for the same field (e.g. via `AbortController` per field) before starting a new one.

This is exactly the "individually-correct pieces, wrong in combination" pattern called out in the brief — the debounce and the blur-commit are each reasonable, and their overlap is what breaks it. It does not violate one of the six enumerated domain rules directly, but it is a real, provable data-loss bug in the one area (document fields) that the organisation edits repeatedly over multiple sessions.

## What I checked and found sound

- **`lib/domain/assessment.ts`** — no partial credit (unmet = any applicable sub-statement not `true`), red-line override computed before the band, 6.3's applicability keyed only off `consequentialDecisions === "no"` (so "don't know" correctly stays applicable), verdict logic (`score === 8` required for "met", any red-line failure forces "not-met" regardless of score). Matches domain rules 1–4 exactly, including the deliberate 7/8-still-not-met case.
- **`lib/domain/checklist.ts`** and **`lib/domain/pack.ts`** — pure, take `now`/inputs as arguments, no hidden clock or randomness; `buildPack` assembles the assessment once at generation time and nothing downstream re-derives or mutates it. `assess()` is called once per `buildPack` call and the result is stored verbatim in `GeneratedPack.assessment`; no code path in the checklist/document-field/email-consent write paths (`lib/storage/packs.ts`) touches `pack.assessment` — each spreads `...existing` and only overwrites its own field. Ticking a checklist item cannot change the score.
- **`lib/storage/packs.ts` / `lib/storage/packs-pure.ts`** — all four write paths (`savePack`, `saveChecklistState`, `saveDocumentField`, `saveEmailConsent`) recompute `expirationTtlSeconds` via `ttlSecondsRemaining(existing.createdAt, now)` — never from `now` alone — so editing a checklist or a policy field cannot extend the 12-month KV TTL. `accessExpiresAt` (90-day link window) is set once in `savePack` from `pack.createdAt` and is only ever read, never recomputed on any of the four write paths or on `loadPack`. Boundary check in `isAccessExpired` is `now >= accessExpiresAt` (correct: expires *at* the deadline, not one tick before).
- **`lib/tailoring/index.ts`, `prompt.ts`, `fallback.ts`, `validate.ts`, `cache-key.ts`** — the previously-found "degraded result cached" bug is fixed: `tailorUnsafe` only writes to the KV cache when `Object.values(result.provenance).some(p => p === "model")`, i.e. a fallback-only result is never cached. `buildTailoringMessages` never puts document fields or arbitrary free text into the prompt — only closed wizard enums plus the org name, which is confined to a delimited `<organisation_name_untrusted_data>` block, newline-collapsed and length-capped before insertion. Layer-2 boundary checks (`validateSlotText`/`BANNED_PATTERNS`) reject obligation language, named laws/regulators, numbers, and markdown, with fallback per-slot on any rejection — consistent with rule 6.
- **`components/use-tailoring.ts`** — the previously-found StrictMode-guard/AbortController deadlock is fixed via the shared `inFlight` map keyed by `${createdAt}:${contentVersion}`: a remount joins the existing promise rather than aborting it, and only the `live` flag (not the request) is used to ignore a late result after unmount. A failed request is deliberately evicted from the map so a later visit can retry; a successful one is kept so a remount is free.
- **`components/document-fields-context.tsx` — the multi-provider issue.** The previously-found "two independent state providers overwrite each other" bug is fixed structurally: a nested `DocumentFieldsProvider` detects an existing context via `useDocumentFieldsContext()` and renders as a no-op passthrough, so `PackResult` wrapping both the policy and staff-note documents in one provider is enough to guarantee a single source of truth for fields shared between the two documents (`[role]`, `[date]`, `[name]`). Hook-order is preserved (the early-return happens after every hook call). No missing cleanup: the only side-effecting resource here is `timersRef`'s `setTimeout` handles, which are cleared per-field before being replaced (`clearTimeout` in both `setValue` and `commit`); there is no `useEffect` in this file, so there is no unmount-cleanup gap to check for other than the timers, and an in-flight `setTimeout`/`fetch` firing after unmount is harmless in React 18 (no state-update-after-unmount warning, and the fetch is not tied to a component instance).
- **`lib/api/rate-limit.ts`** — the fixed-window bucket arithmetic (`windowBucket`) and TTL padding are correct; the acknowledged read-then-write race (two requests can both read the same count and both be admitted) is explicitly documented as an accepted trade-off, not a silent bug. The in-memory fallback correctly filters by both cutoffs, floors bucket growth via `MAX_TRACKED_KEYS`, and `checkRateLimitKv`'s two-window check short-circuits on the tighter (minute) window first.
- **`content/v1/scoring.ts` `bandForScore`** — the four bands (`0–2`, `3–5`, `6–7`, `8`) are contiguous and exhaustively cover every integer 0–8 with no gaps or overlaps; an out-of-range score throws rather than silently mis-banding.
- **`app/api/*/route.ts`** (`packs`, `tailor`, `checklist`, `document-fields`, `email-link`) — all validate with closed (`.strict()`) Zod schemas, reject malformed JSON, check token shape before any KV read, and return the right not-found/expired/429 status codes. `document-fields`'s `fieldId` is restricted to the declared enum (`ALL_BRACKET_FIELD_IDS`), so this endpoint cannot be used to write arbitrary keys into a stored pack. `email-link` records consent even when sending is unconfigured, and never echoes the address back on a send failure. `tailor`'s route re-derives the assessment server-side from the same payload rather than trusting a client-supplied unmet-controls list, so a hand-crafted POST cannot steer which controls are described to the model.
- **`lib/storage/token.ts`, `lib/cloudflare/kv.ts`, `lib/api/admin-auth.ts`** — token generation/validation, KV 404-vs-error handling (a corrupt JSON body degrades to "absent" rather than throwing into a page render), and the admin passcode's timing-safe, fixed-length comparison (including the hex-length/format guard before `timingSafeEqual`, which would otherwise throw on a malformed cookie) are all correct.
- **`components/pack-flow.tsx`, `components/pack-result.tsx` (checklist toggle), `components/save-pack.tsx`** — the checklist's optimistic toggle correctly reverts to the pre-toggle value on failure and is guarded per-item by `pendingIds` (the checkbox is disabled while its own request is in flight), so — unlike the document-fields bracket — a second toggle of the *same* item cannot be fired before the first settles. No state updates after unmount were found in these components (none holds a `live`/`mounted` flag because none has an effect whose result is applied asynchronously after the component could have unmounted, except `use-tailoring.ts`, which is covered above).

No further Critical/High findings beyond the one above. I did not find any violation of domain rules 1 (frozen snapshot), 2 (no partial credit), 3 (red-line override), 4 (6.3 applicability), or 5 (TTL/expiry) — those areas read as deliberately and correctly implemented, including the specific edge cases (7/8 with a red-line failure, "don't know" keeping 6.3 applicable, TTL recomputed from original `createdAt` on every one of the four write paths). The one finding above is a Medium-severity-in-isolation client-side race that I am rating High because it causes silent, undetectable loss of a value the user believes they saved, in the newest and least-tested part of the codebase.
